# 账单与付款页面

测试站：https://testmedusa.365d4u.com

## 使用入口

- 管理后台账单：https://testmedusa.365d4u.com/app/invoices
- 独立创建页面：https://testmedusa.365d4u.com/invoices/new/
- 管理员登录资料保存在本机忽略目录 `.private/admin-access.json`。

后台侧栏“账单 / Invoices”可创建和查询账单。创建页为英文界面，只需填写名称和金额，名称默认 Custom Piece，默认一条明细、数量为 1；金额为 USD 最终应收金额，包含需要收取的税费和运费。客户在付款页填写邮箱、收货和账单地址。既有多明细账单仍可正常查看和支付。

创建后会立即生成原生 Medusa 待付款订单和短付款链接，格式为 `/payit/订单号/mo_xxxxxxx`。短码为 mo_ 前缀加 7 位小写字母/数字，总共 10 个字符，后缀不含连字符或下划线；已创建账单自动使用同样格式，旧的 `checkout/order-pay` 链接验证后跳转到短链接，支付返回参数仍保留。短码从原有随机密钥稳定派生，无需重建订单。付款页面与公开账单接口设有访问频率限制。账单列表提供“查看付款页”“复制链接”；原生 Orders 详情也有“账单付款页面”卡片。付款确认后，同一订单更新为已收款，不会另建一张订单。已付款页面显示 Payment received，禁止再次发起收款。

新建原生订单与账单共用递增序列，起点为 **200000**。旧原生订单和导入的 WordPress 历史订单号保持不变；数据库事务失败等情况可能导致正常的序列空号。`apps/backend/src/scripts/set-order-number-start.ts` 只提高序列、不回退现有号码。

## 页面与飞书嵌入

客户付款页复用用户提供的 WordPress order-pay 页结构、样式、页头、保障图片、商品表格和地址区域。旧 WordPress nonce、订单密钥、支付脚本及 iframe 已清除，收款由本项目 Medusa 支付会话接管。信用卡数据进入 Oceanpayment 托管 iframe，不进入本项目后端。

独立创建页面支持移动端，可在浏览器或飞书网页容器打开；允许飞书/Lark 域内的 iframe 嵌入。飞书应用主页 `/app/invoices` 跳转到独立账单页面并启动飞书登录；应用可见范围内的同企业员工自动拥有创建和查看账单权限，完整后台管理权限只授予配置的管理员身份。前台顾客登录与员工登录隔离。原生后台内打开账单则复用后台登录状态。详见 `feishu-sso.md`。Apple Pay 测试域名白名单由用户于 2026-09-23 确认已完成，随后启用入口。

### 订单时间线补全（2026-09-24）

用户指出原先只显示“Change history started”没有业务意义，因此基线记录仅保留在数据库中，API 与界面不再显示。订单详情改为实际事件时间线：已知操作人、支付方式、金额、结果、渠道交易号，以及资料和状态的前后变化；变更明细默认展开，支持全部展开/收起与刷新，手机端不横向溢出。

`invoice-history-recovery.sql` 从旧订单仍存在的创建、支付会话、授权/关闭时间、capture、refund、地址快照、Ocean 回执和通知记录恢复事件，使用原记录时间，标注 `Recovered record`。恢复项有唯一键，重复部署不会重复插入，不发送邮件、不触发收款。只恢复详细审计启用之前的记录；快照明确标记为最后保存的值，不伪造前值或无法查证的历史操作人。

新日志增加付款成功邮件/队列的排队、发送、重试和结果；既有订单/地址/支付/退款/Email/Note 的字段审计继续保留。公开付款 API 在付款链接校验通过后记录提交、重选、确认的请求和处理结果，用请求编号关联，并保留已知业务校验失败原因。操作人标记为使用付款链接的客户，不误认为已认证员工；服务器未收到的浏览器本地校验不属于服务器记录。请求失败不等于银行拒付或取消，文案明确区分。原始支付请求、凭据、完整卡号及未知渠道异常正文不写入日志。

### 操作人显示规则

公开付款页面无需登录；提交、支付方式重选和付款确认请求的内部来源仍是 `payment_link`，界面统一显示 **User**。后台账单创建、Email/Note 修改、额度豁免和原生订单/支付状态操作使用服务器已验证的员工 ID，解析对应飞书登录名，禁止从请求正文指定操作人。

新审计记录保存 `actor_name_snapshot`，姓名修改后仍保留操作发生时的署名；旧记录有已知员工身份时从飞书绑定关系解析姓名。原生后台订单取消/完成、收款、退款等成功请求另存 Staff action，包含请求前后状态和实际登录者，补足 Medusa 部分接口不保存 changed_by 的情况；不把并发或异步的其他数据库事件强行归给该员工。原生 `order_change` 的创建、请求、确认、拒绝和取消身份也接入审计。后台自动处理、渠道回调以及无法查证来源的旧事件不伪装成某位员工操作。

测试覆盖公开页面不进入 Staff 审计、原生后台取可信飞书姓名而非伪造正文、发送成功响应前保存日志、独立/原生两类身份解析及改名后历史署名保留。

## 支付方式重选（2026-09-23）

- 点击付款提交前，允许选择 PayPal 或信用卡。点击付款且通过地址校验后，本页锁定付款按钮和支付方式，不再通过原先的 5 秒定时器自动解锁。SDK 明确报错/拒绝后可重新选择；刷新或新开标签页恢复选择入口。已付款账单不再展示支付入口，付款和切换 API 都拒绝重复操作。
- 每次实际切换支付方式增加 `payment_version`。提交必须同时匹配当前版本与支付方式；旧标签页和已切换掉的请求不能发起新的本站付款。即使切换回同一种方式，旧版本也不能复用。
- 按用户最终要求，**不调用 Oceanpayment 取消接口**。仅更新本站选择；旧信用卡会话保留，以处理延迟通知。账单直接使用 Medusa Payment Module 创建会话，避免通用 `createPaymentSessionsWorkflow` 自动删除所有旧会话。未付款 PayPal 会话可移除，本站不会再对其执行 capture。
- 完成付款时，优先核验任一信用卡尝试的已签名成功通知，然后才处理当前有效会话。一次确认收款后，本站停止发起任何新付款。
- 边界：重选不能作废已打开的 Oceanpayment/银行验证页面；渠道中已在途的多笔交易仍可能先后扣款。本站的版本校验和已付款拦截不能代替渠道撤销。用户已明确要求不再调用取消接口。真实重复扣款需按渠道回执人工核对，不能丢弃旧回执，也不能把本地旧请求失效描述为银行页面失效。

最终验证：17 项自动检查和生产构建通过；#200011 用 UI 挂起测试验证提交前可选、提交后超过 5 秒仍锁定、刷新和新标签页可选，并验证银行卡字段错误后刷新可改选 PayPal。#200013 验证 PayPal→信用卡→PayPal 重选、并发切换只接受一个版本、旧页面提交被拒绝；信用卡处于 3DS 中时改选 PayPal成功，之后旧信用卡完成沙箱 $1 付款，同一账单正确记为 paid，后续两种方式均被拒绝。这个测试同时验证了旧银行页面确实没有被取消。
